# CHAPTER 5. MCP Figma 연동 — 기획자가 화면을 완성한다

> 기획자가 기능·정책·인터랙션을 담은 화면을 직접 그리고, 디자이너는 컴포넌트 통일성을 검토한다

## 🗺️ 기획자와 디자이너의 역할 분담

일반적으로 "기획자가 Figma를 쓴다"고 하면 **간단한 레이아웃 스케치 수준**을 떠올리기 쉽습니다. 하지만 실제 업무에서의 역할 분담은 다릅니다.

| 구분 | 기획자 (주도) | 디자이너 (검토) |
| --- | --- | --- |
| **화면 구조** | 전체 레이아웃, 영역 구성, 입력 요소 배치 직접 설계 | 기존 컴포넌트와의 일관성 검토 |
| **기능 및 정책** | 각 UI 요소의 동작 조건, 유효성 검사, 상태값 정의 | 시각적 피드백(에러 상태 등) 표현 방식 제안 |
| **인터랙션** | 토글·모달·활성화 조건 등 인터랙션 흐름 정의 | 애니메이션, 전환 효과 등 디자인 디테일 보완 |
| **텍스트/레이블** | UX 문구, 안내 텍스트, 에러 메시지 직접 작성 | 서비스 전체 톤앤매너 관점 검토 |
| **서비스 통일성** | 기존 화면 패턴 참고하여 설계 | 전체 서비스 디자인 시스템 기준으로 최종 정합 |

:::info 🧭 기획자가 주도한다 — Claude Code + Figma MCP는 도구일 뿐이다

Claude Code와 Figma MCP를 연동하면 기존 컴포넌트를 빠르게 분석하고 화면 초안을 빠르게 그릴 수 있습니다.  
하지만 **서비스를 가장 깊이 이해하는 사람은 기획자**입니다.

기획자는 서비스의 기능 구조, 사용자 흐름, 예외 케이스, 정책 결정 맥락을 모두 알고 있습니다.  
AI가 아무리 빠르게 초안을 만들어도, **그것이 올바른 방향인지 판단하고 원하는 대로 조율하는 것은 기획자의 역할**입니다.

**Claude Code + Figma MCP는 기획자의 생산성을 높이는 도구입니다.  
화면 설계의 주도권은 항상 기획자에게 있습니다.**
:::

:::tip 💡 Figma MCP가 이 구조에서 하는 역할
기획자가 이미 서비스 기능과 정책을 가장 잘 알고 있습니다. Figma MCP는 **기획자가 기존 디자인 시스템의 컴포넌트 구조와 패턴을 정확히 파악한 상태에서 화면을 설계**할 수 있도록 돕습니다. 결과적으로 디자이너의 검토 부담이 줄고, 기획-디자인 간 불일치로 인한 재작업이 감소합니다.
:::

## 🔌 Figma MCP 연동 방법

Figma MCP는 **읽기 전용(read-only)** 연동입니다. Claude Code가 Figma 파일의 컴포넌트·레이어·노드 구조를 읽어와 기획 설계에 활용하는 방식입니다.

### 사전 준비

| 항목 | 내용 |
| --- | --- |
| **Figma Personal Access Token** | Figma 계정 → Settings → Personal Access Tokens에서 발급 |
| **Figma 파일 공유 URL** | 분석할 파일 또는 특정 프레임의 URL (node-id 포함 권장) |
| **MCP 서버** | Figma 공식 MCP 서버 (`https://mcp.figma.com/mcp`) 사용 |

### 설정 예시

```json
// ~/.claude.json (mcpServers 항목에 추가)
{
  "mcpServers": {
    "figma": {
      "type": "http",
      "url": "https://mcp.figma.com/mcp",
      "headers": {
        "X-Figma-Token": "YOUR_FIGMA_PERSONAL_ACCESS_TOKEN"
      }
    }
  }
}
```

> ⚠️ **Figma MCP 주요 제한사항**  
> • `get_design_context` 도구는 대용량 파일에서 타임아웃이 발생할 수 있습니다.  
> • 이 경우 **`get_screenshot` + 특정 node-id 지정** 방식이 더 안정적으로 동작합니다.  
> • Figma 파일을 직접 수정하거나 새 프레임을 생성하는 기능은 지원하지 않습니다 (읽기 전용).

## 🛠️ 실전 활용 사례 — Pub/Sub Access Key 인증 화면 기획

KakaoCloud Pub/Sub 서비스의 **Push Subscription 생성 화면에 Access Key 인증 기능을 신규 추가**하는 기획 작업에서 Figma MCP를 활용했습니다.

### 배경 및 목표

:::tip 📋 작업 배경
- GCP JWT 방식 vs AWS Firehose Access Key 방식 비교 분석 후, **Access Key 방식 도입 결정**
- 기존 Push Subscription 생성 화면에 인증 설정 UI 영역을 신규 추가해야 함
- 기획자가 **기능 정책·인터랙션·UX 문구까지 직접 정의**한 화면 기획서를 작성
- 디자이너는 KakaoCloud 콘솔 디자인 시스템 기준으로 컴포넌트 일관성만 최종 검토
:::

### Figma MCP를 활용한 기획 작업 흐름

| 단계 | 작업 | 내용 |
| --- | --- | --- |
| **1** | 기존 화면 컴포넌트 분석 | Figma MCP로 Push Subscription 생성 화면의 기존 컴포넌트 구조·패턴 파악 |
| **2** | 기능 정책 정의 | 인증 사용 여부, 입력 방식(직접/Secrets Manager), 마스킹 처리, 재조회 불가 정책 등 직접 정의 |
| **3** | 인터랙션 설계 | 인증 영역 활성화 조건, 입력 방식 전환 시 UI 변화, 갱신 모달 흐름 등 인터랙션 정의 |
| **4** | UX 문구 작성 | 레이블명, 안내 문구, 에러 메시지, 마스킹 안내 텍스트 등 직접 작성 |
| **5** | 화면 기획서 완성 | 위 내용을 종합한 기획서를 Confluence에 즉시 작성 (MCP 연계) |
| **6** | 디자이너 검토 요청 | 완성된 기획서 기준으로 디자이너가 컴포넌트 통일성·디자인 시스템 적합성만 검토 |

### 실제 설계된 화면 구조 (텍스트 와이어프레임)

```
┌─────────────────────────────────────────────────────┐
│ Push Subscription 생성                               │
├─────────────────────────────────────────────────────┤
│ 구독 이름  [________________________]                │
│ 토픽       [________________________]                │
│ 구독 유형  ● Push                                    │
│                                                     │
│ Endpoint URL                                        │
│ [https://my-service.example.com/push___________]    │
│                                                     │
│ ┌─ 인증 설정 (선택) ────────────────────────────┐   │
│ │ 인증 방식   Access Key                        │   │
│ │            (현재 단일 방식 고정 레이블 표시)    │   │
│ │                                              │   │
│ │ Access Key 입력 방식                          │   │
│ │ ● 직접 입력                                  │   │
│ │ ○ Secrets Manager에서 가져오기               │   │
│ │                                              │   │
│ │ Access Key [____________________] [표시]     │   │
│ │ ※ 등록 후 다시 조회되지 않습니다.             │   │
│ └───────────────────────────────────────────────┘   │
│                                                     │
│                          [취소]   [구독 생성]        │
└─────────────────────────────────────────────────────┘
```

### 기획자가 직접 정의한 정책 및 인터랙션

| 항목 | 기획 내용 |
| --- | --- |
| **인증 방식 표시** | 현재 단일 방식이므로 드롭다운 대신 고정 레이블 "Access Key"로 표시. 향후 방식 추가 시 드롭다운으로 전환 예정 |
| **입력 방식 전환** | 직접 입력 선택 시 텍스트 입력 필드 활성화. Secrets Manager 선택 시 Secret 목록 드롭다운으로 UI 전환 |
| **Access Key 마스킹** | 입력 즉시 마스킹 처리(●●●●●●●●). [표시] 버튼 클릭 시 일시적으로 원문 확인 가능 |
| **재조회 불가 정책** | "등록 후 다시 조회되지 않습니다" 안내 문구 필수 노출. 보안 원칙에 따라 저장 후 원본 값 반환 금지 |
| **갱신 인터랙션** | 상세 화면 [갱신] 버튼 클릭 시 새 key 입력 모달 표시. 저장 즉시 Push Agent에 반영 |
| **인증 해제 정책** | 수정 화면에서 인증 영역 제거 가능. 해제 전 "인증이 해제됩니다" 확인 모달 표시 |
| **Secrets Manager 연동** | 선택 시 현재 프로젝트 Secret 목록 드롭다운 제공. `{"api_key": "..."}` 포맷 안내 문구 함께 표시 |

## 🤝 Figma MCP가 기획-디자인 협업에 미치는 영향

| 시점 | 기존 방식 | Figma MCP 활용 후 |
| --- | --- | --- |
| **기획 단계** | Figma를 직접 열고 기존 화면 탐색하며 컴포넌트 파악 (시간 소요) | MCP로 컴포넌트 구조 즉시 파악 → 기획 설계에 바로 반영 |
| **디자이너 전달** | 텍스트 기획서만 전달 → 디자이너가 화면 구조 재해석 필요 | 기능·정책·인터랙션·문구 완비된 기획서 전달 → 디자이너는 통일성 검토만 |
| **수정 사이클** | 기획 의도 오해 → 디자인 재작업 발생 | 기획 의도가 명확히 기술된 기획서 → 재작업 감소 |
| **개발 핸드오프** | 기획서·디자인 간 정책 불일치 발생 가능 | 기획서가 정책 기준 문서 역할 → 개발 핸드오프 품질 향상 |

:::tip 💡 Figma MCP 활용 핵심 포인트
- Figma MCP는 기획자가 **기존 디자인 시스템의 컴포넌트 구조와 패턴을 정확히 파악**하도록 돕는 도구입니다.
- 기획자는 이를 바탕으로 **기능·정책·인터랙션·UX 문구까지 완성된 기획서**를 작성합니다.
- 디자이너는 기획서를 기준으로 **전체 서비스 디자인 시스템 관점의 일관성만 검토**하면 됩니다.
- 대용량 파일에서 `get_design_context`가 타임아웃 나면 **`get_screenshot` + 특정 node-id**로 접근하세요.
- Confluence MCP와 함께 쓰면 **컴포넌트 분석 → 기획서 작성까지 한 흐름**으로 완료됩니다.
:::

| **기존 컴포넌트 파악** | Figma 직접 탐색하며 패턴 파악 (~30분) | MCP로 구조 즉시 분석 (~5분) | **83% ↓** |
